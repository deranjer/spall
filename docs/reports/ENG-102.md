# ENG-102 (R4c) — Lighting cache: hitch-free scroll, latency, lamp content

Remainder of the R4 lighting-cache work after ENG-101. **Implemented and partly
validated (headless GPU tests); not accepted.** Nothing here claims a G2
result; hardware numbers are from one machine (RTX 4080 SUPER, D3D12).

## 1. Camera scroll: re-centre into a back result set

**Problem.** When the camera drifted 8 m from the cache centre the client sent a
grid at a new origin and the cache recomputed in one dispatch (a single frame
carrying the whole recompute, the ~28–32 ms hitches seen in ENG-101's live runs
before the "send only when changed" fix).

**Change (`spall_render::sky_visibility`).** Two result sets (visibility + bounce
radiance) plus one shared occupancy buffer. A grid at the *same* origin is a
terrain edit: sliced sweep in place (unchanged). A grid at a *different* origin
is a re-centre: its occupancy is applied when its turn comes, the sliced sweep
(16 z slices per frame, 8 frames) writes the **back** set, and only when the last
slice is recorded does the front index flip and the shading globals take the new
origin. Shading therefore never samples a half-moved cache and keeps the old,
consistent lighting until the swap. Compute and shading have separate global
buffers, because the compute needs the new origin while shading still needs the
old. A grid arriving during a re-centre replaces the queued one (newest wins);
bodies that move during one are re-laid over the new occupancy at the swap and
lit by a follow-up sweep only if they actually moved.

**Cost.** Memory 72 → 136 MiB (a second result set: 2 × 64 MiB visibility +
radiance for 128³ cells, plus 8 MiB occupancy), reported in the client line.

**Evidence** (`dynamic_lighting_gpu`, GPU, `--ignored`):

- `scrolling_the_cache_swaps_in_one_consistent_frame`: the cache moves 8 m/4 m and
  the new grid drops a slab that shaded the ground. 7 frames still show the old
  cache with a **worst mean pixel difference of 0.000** from the pre-scroll frame,
  the sweep takes 8 frames, and after the swap the ground is lit (0.058 → 0.462).
- `a_body_arriving_during_a_scroll_is_lit_after_the_swap`: a slab appearing on
  frame 3 of a scroll shades the ground afterwards (0.462 → 0.058).

## 2. Measured edit latency

> **2026-09-26 correction:** the original 83 ms figure here was *cache arrival to
> the last sweep slice being recorded* only — not edit-to-visible latency, and
> mislabeled as such. The client's report-line field was renamed to
> `cache update to last slice recorded, not presented` (see the ENG-95 pass). The
> correlated, end-to-end measurement below replaces it.

### 2a. Cache-only figure (superseded, kept for continuity)

`a_terrain_edit_is_lit_within_one_sweep`: a roof appears over open ground; the
lighting cache alone is updated after **8 frames / 83.0 ms** on the CPU clock
(cache arrival to the last slice being recorded; excludes GPU finish and
present). The headless frames in that test include a full-frame readback and ran
at 11.6 ms mean / 13.0 ms worst.

### 2b. Correlated end-to-end: authoritative commit → presented pixel

`examples/sandbox/tests/lighting_latency.rs`
(`cargo test -p sandbox --features client --test lighting_latency`, debug
build): a real QUIC server hosts `fixtures/lighting-room`'s sealed house; a real,
separate "actor" client cuts a hole in its roof; a real "observer" client (the
production network/replica code) receives the change, and its lighting cache is
driven through the exact `spall_client::window::rebuild_pass` / `build_instances`
/ `sky::build_sky_occupancy` functions the interactive window itself calls
(pulled out of `window.rs` into standalone functions for this — no
re-implementation) rather than a stand-in. Every stage is timestamped on **one
process's one monotonic clock**: server, both clients and the renderer all run as
threads of the test binary, so the subtractions below are valid; a real
deployment's server and client are on different machines with real network
latency and clock skew this does not model, stated as a limit, not modelled away.

| Stage | Player moving | Player stationary | How measured |
| --- | ---: | ---: | --- |
| commit → client receipt | 132–172 ms | 121–156 ms | event (commit handler) → polled (`terrain_hash()` change, ~0.2 ms granularity) |
| receipt → rebuild dispatched | 0.0 ms | 501.1–501.2 ms | reproduces `window.rs`'s real `moved_far_enough` / `due_for_recheck` gate at the real `TERRAIN_RECHECK_INTERVAL` (500 ms) constant |
| dispatch → rebuild done | 1408–1703 ms | — | `rebuild_pass` (terrain instances + sky occupancy from the replica), **debug build** |
| rebuild → cache uploaded | 1.8–3.6 ms | — | `set_terrain` + `set_sky_occupancy` calls returning (not GPU-finished) |
| upload → lit (sweep) | 87.7–143.1 ms | — | `lighting_is_sweeping()` polled every headless frame |
| lit → presented | 3.8–9.7 ms | — | one more render (headless: no vsync/present wait, see limits) |
| **total, commit → presented** | **1.7–2.0 s** | **2.4–2.5 s** | |

**The `TERRAIN_RECHECK_INTERVAL` polling contribution is confirmed directly**:
the stationary run's receipt→dispatch stage measured 501.1–501.2 ms, matching the
constant it reproduces almost exactly (this is the real gate reproduced with the
real constant, not an estimate). A moving player pays 0 ms here (the very next
frame's `moved_far_enough` fires the dispatch). **It is not the dominant term**:
even the worst case (~501 ms) is smaller than the rebuild stage below, so a
revision-driven push instead of this poll would help but is not the
bottleneck the way the brief's question anticipated.

**The rebuild stage, not the poll, dominates** (1.4–1.7 s of the 1.7–2.5 s
total) — and this number is a **debug build**, walking `lighting-room`'s three
26×26×12 houses plus a 160×160-cell lawn into cube instances and a sky-occupancy
grid on one CPU thread. ENG-101/102's earlier release-vs-debug spot check on a
much smaller diff (200 moving bodies) showed roughly a 4× debug penalty; this
stage does far more raw geometry walking than that case, so a proportionally
larger gap here is plausible but **the release number itself is unmeasured**: a
release rebuild of this same test needs `target/release/sandbox-client.exe`,
which a running `sandbox-client.exe` process (not started by this session) held
locked for the duration of this pass, blocking the rebuild. This is the next
thing to measure, not a diagnosed bottleneck — do not read the debug figure as
representative of a real session's cost.

**Limits of this measurement:**
- Debug build only (see above).
- "Presented" is one more headless render with no vsync/compositor wait; a real
  window's present can add a variable few-to-tens of ms (ENG-101 noted headless
  vs. live-window GPU cost already differs).
- Client receipt is polled (~0.2 ms sampling error), not event-driven.
- One scene, one edit shape (a small roof cut); not continuous motion or rapid
  repeated edits (see §2c).

### 2c. Body-motion latency, measured separately

Body/terrain-edit latency are different mechanisms in this cache (bodies never
touch the network-edit path above) and are kept separate rather than mixed into
one figure:

- **Typical and worst case, a single moving body**: `moving_bodies_cost_per_frame`
  — 200 moving bodies, 1080p, release-representative GPU cost: sky 0.58 ms /
  bounce 2.18 ms per-frame slice, sweep 8 frames (a body's own light lands up to
  8 frames / ~133 ms at 60 fps after it moves, plus up to 8 more if a sweep was
  already running when it moved — the general bound from ENG-101, reconfirmed
  here).
- **A change landing during an already-running, unrelated sweep**
  (`a_change_arriving_during_an_active_sweep_is_not_lost`, new): a terrain edit's
  sweep is one frame in when a body lands elsewhere; both changes are correctly
  reflected once sweeping stops (15 frames total to both, ~139 ms wall clock from
  the body's arrival) — nothing is dropped, and the renderer's own
  `lighting_latency_ms()` counter is available (reflects the more recent change,
  not stuck on the older one).
- **Continuous motion**: `rapid_motion_settles_to_the_final_pose_with_no_ghosts`
  (existing, ENG-101) — 30 frames of continuous motion then settling matches a
  fresh render at the final pose exactly (mean diff 0.0000); no accumulated
  drift or ghosting from sustained movement.
- **Rapid edits**: `moving_bodies_cost_per_frame`'s 200-body-per-frame diff is
  the rapid-edit stress case already in the suite; the sky/bounce per-slice GPU
  cost above is the relevant number (CPU-side diffing cost is reported
  separately in that test's `set_bodies` timing).
- **Repeated camera re-centring**
  (`repeated_camera_recentres_each_complete_and_the_last_one_wins`, new): three
  back-to-back re-centres (each landing ~2 frames apart, inside the 8-frame
  sweep an earlier one is still running) all complete — no stuck or dropped
  re-centre — in 10 frames total, and the *last* one's grid is what shading ends
  up showing (luma 0.392 at a point only the last centre's flat-ground grid
  would light).

## 2d. Dirty-bounds cull: not pursued this pass

The brief asked to choose this from complete measurements rather than the
isolated cache number. With the correlated data above, the sliced full sweep
(87–143 ms) is a minority of the total edit latency (1.7–2.5 s, dominated by the
unmeasured-in-release rebuild stage) and is not what a player would perceive as
the slow part. Cutting the sweep to a dirty region would not move the total by a
visible amount at current (debug, worst-case) proportions; revisit after a
release-build rebuild measurement, and only if the rebuild stage itself is
brought down first (moving it off the once-per-500ms/move-triggered path would
matter far more).

## 3. Low-angle sampling

The bounce pass now casts 66 rays per cell (was 14, then 42): 14 missed surfaces
below ~35° from the face plane, blocky bleed at grazing angles. Recompute cost
measured at 3.37 ms of GPU time for a full bounce; `bounce_gpu` (8/8) keeps the
furnace calibration and the low-angle checks.

## 4. Emissive content

The sandbox manifest v4 adds `LAMP` (id 200, emissive), and the lighting-room
fixture's doorway house carries a 1 m emissive lamp (F4/F5/F6 show it: bounce
off, sky visibility, indirect).
