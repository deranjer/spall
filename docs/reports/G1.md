# G1 CPU-side evidence — ENG-18

Date: 2026-09-09 (cross-brick scene + reordered-snapshot + exact-replay additions)

The tracked `g1-networked-destruction` fixture drives two real `sandbox-client`
OS processes against a real `sandbox-server` over QUIC. It runs on the
**cross-brick** `cross_brick_bridge_scene`: a single column straddling the
`x = 32` brick boundary holds up a beam that also spans both bricks, over an
anchored floor. Client 0 cuts the seam column to detach the beam and both
clients excavate opposite ends of the floor concurrently; client 0 then carves
the falling beam again with a body-targeted cut while it is still moving.

The harness passes only when:

- every one of the ten scripted cuts commits (`transactions_committed >=` the
  cut count — a run that quiesces early therefore fails);
- the server and both clients agree on the final canonical topology hash;
- the detached body's cells were owned **across a brick boundary** — the
  server reports the largest detached body spanning `>= 2` distinct bricks
  (cross-brick structural-support propagation and brick-boundary ownership
  transfer);
- each live client observes the beam move at least
  `minimum_body_displacement_m` (0.3 m);
- the body-targeted cut is accepted against the detached body (that body loses
  solid cells afterwards) on at least one replica;
- the committed topology-event stream, replayed deterministically from the
  tick-0 baseline through the durable journal (`sandbox-server --replay`),
  reproduces the live run's canonical hash.

The `--loss-percent 2` variant additionally requires the live clients to have
observed motion-snapshot datagrams delivered out of `snapshot_seq` order (the
per-client UDP proxy deterministically holds every third server->client
datagram past the 20 Hz snapshot spacing).

client 1's replica had not re-observed that specific body between applying the
split transaction and its final snapshot. The gate requires the cut to land on
*some* replica and the hashes to agree, both of which hold.

## Exact-replay mechanism

The harness runs the server with `--save` and `--checkpoint-interval-ticks 0`,
so the world database holds a tick-0 baseline checkpoint plus a journal of
every committed transaction. After the session, `sandbox-server --replay`
opens that database, recovers from the **oldest** checkpoint
(`spall_store::recover_from_base`), replays the entire committed-transaction
journal onto it (`spall_server::persist::replay_from_base_builtin`, the same
`replay_transaction` fold the durable-recovery path uses), and compares the
rebuilt canonical topology hash against the live agreed hash.

## Physics fix (carried from PR #50)

The scenario previously crashed intermittently in Rapier's CCD sweep
(`ccd/sweeps.rs: "No element at index"`) when the terrain collider was rebuilt
on a committed cut. No body in these scenes enables per-body CCD, so the server
runs the built-in scene with the CCD solver pass disabled
(`PhysicsConfig::disable_ccd`). Topology hashes and tick counts are unchanged
with the pass on vs off. The projectile-CCD physics report keeps the pass.

## Detached beam coming to rest on remaining structure (ENG-61)

The `g1-networked-destruction` run ends on **edit**-quiescence (~tick 130) — a
fixed number of idle ticks after the last committed cut — which is while the
detached beam is still mid-fall, so that run alone shows no "at rest" state.
This was previously mis-attributed to a physics-engine defect ("the beam
free-falls forever"); it is not. Given ticks to settle, the beam comes to rest
on the remaining floor with no engine change:

- **CPU-side:** the `spall_sim` `body_rest_on_structure` integration test drives
  one authoritative `Simulation` through the cut script headless and steps
  physics on. The cross-brick beam (bottom at `y = 1.75 m`) settles on the
  floor top (`y = 0.5 m`) — a 1.25 m drop of the body origin — asleep, linear
  speed `< 0.02 m/s`, `max_penetration_m < 0.15` (on the floor, not through it),
  with the floor span under the beam still solid.

- **Networked:** the `body-rest-on-structure` fixture (sibling of
  `g1-networked-destruction`, same cross-brick scene) severs the seam column,
  excavates only the floor ends *outside* the beam span, and runs the server
  with `--await-body-settle`, which keeps stepping physics past edit-quiescence
  until every detached body is asleep and has held its origin still for
  `AWAIT_SETTLE_STABLE_TICKS` (60) ticks, bounded by `--ticks`. The session
  harness then requires the server's end-of-run report to show the beam
  settled. Measured (loopback QUIC, seed 1, 3/3 runs):

  | Result | Server ticks | Committed | Brick span | Replay | disp c0/c1 | detached bodies asleep | max final speed | stable ticks | max penetration | resting origin y | Final hash |
  | --- | ---: | ---: | ---: | :-: | ---: | :-: | ---: | ---: | ---: | ---: | --- |
  | passed | 97 | 6 / 6 | 2 | 6 events → match | 1.24 / 1.24 m | yes | 0.000 m/s | 60 | 0.000 m | −1.250 m | `35489de86817a69b96aee6a30b8d4422b53b7d81fb19cce7d440e8ad1c53efc3` |

  `resting origin y = −1.25 m` is the beam origin dropping exactly onto the
  floor top; `max penetration 0` confirms it rests on the floor rather than
  clipped through it.

Note: over-excavating the floor *corner* (as `g1-networked-destruction`'s
`[22,0,0]` cut does after several adjacent cuts) legitimately detaches a
1-cell floor chip with nothing beneath it, which then correctly free-falls —
that is expected physics, not the beam. `body-rest-on-structure` keeps its
excavation clear of the beam's support so the only detached body is the beam.

## Commit latency and admission accounting (ENG-62 / T11a increment 1)

`ServeSummary` is now `version: 3`. Every `serve` run measures **server commit
latency** — wall-clock from the tick the host admitted an `ActionRequest` for
staging to the tick its transaction committed — and buckets each sample by the
shape of the commit (`crates/spall_server/src/commit_latency.rs`):

- **single-brick commit** — no structural split (`Committed::bumped_epoch ==
  false`); gate target p95 `<= 100 ms` (no network delay).
- **structure split** — a split whose detached geometry is under 2048 cells;
  gate target p95 `<= 500 ms`.
- **large collapse** — a split at or over 2048 cells (near the 4096-op inline
  transaction budget); gate target `<= 2000 ms` before consistent activation.

The summary also carries the gate's **requested / rejected / queued /
committed** breakdown: `actions_requested` (every inbound `ActionRequest`,
retries included), `actions_rejected`, `actions_staged`,
`actions_queued_unresolved` (staged but not committed at end of run), and
`transactions_committed`.

A scenario file opts into the assertion with a `latency_targets` block; the
`cargo xtask scenario` harness then fails the run if any *exercised* bucket's
measured p95 exceeds its target (a bucket with no samples cannot fail). The
session summary's `admission` object records the counts, the measured p95s, and
`latency_targets_met`.

### Measured — `g1-networked-destruction`, loopback QUIC, this machine

Windows 11, seed `0x5A11…0011`, `--paced`, two real OS clients.

| Run | requested / rejected / queued / committed | single-brick p95 (n) | structure-split p95 (n) | large-collapse p95 (n) | targets met |
| --- | --- | --- | --- | --- | :-: |
| `--loss-percent 0` | 10 / 0 / 0 / 10 | 39.1 ms (8) | 56.3 ms (2) | — (0) | yes |
| `--loss-percent 2` | 10 / 0 / 0 / 10 | 39.2 ms (8) | 55.2 ms (2) | — (0) | yes |

Both cuts that split (the seam-column cut that detaches the beam, and the
body-targeted recut) land in the structure-split bucket; the other eight cuts
are single-brick edits. The clean run reproduces the recorded topology hash
`62164eee…` and exact-replay match; the impaired run's final hash still varies
run to run with proxy timing (pre-existing — only the clean run is
deterministic), all ten cuts commit either way.

The **large-collapse bucket has no samples** on this fixture: its scene is the
small cross-brick bridge, and — more fundamentally — a cut that detaches a
large connected body is *rejected* today by `ReplicationError::SplitTooLarge`
(`MAX_TRANSACTION_OPS = 4096`; the T17 baseline-blob path for an oversized
split is unimplemented). Exercising that bucket is blocked on that work.

## Graphical destruction capture (ENG-62 / T11a increment 2)

`cargo xtask capture --scene destruction` (→ `sandbox-capture --scene
destruction`) drives the authoritative `spall_sim` world on the same
`cross_brick_bridge_scene` through the `g1-networked-destruction` cut script and
renders **offscreen frames of the real destruction**: the live terrain volume
and every detached body — meshed from the authoritative world with
`spall_mesh::build_volume_mesh`, each body placed at its current physics pose —
are handed to the T12 `spall_render` pipeline (`capture_scene`), which reports
**measured GPU render-pass timings** from timestamp queries. Frames are captured
at ticks 3 / 20 / 45 / 90 / 190 (pre-cut, mid-sever, beam detached, mid-fall,
settled) against a fixed camera framed on the initial scene, so the beam is seen
to drop. Exit 3 without a usable GPU/driver; the run writes `summary.json` plus a
`tick_NNN/shaded.png` per frame.

Windows 11, **NVIDIA RTX 4080 SUPER, D3D12** (Vulkan on this adapter is blocked
by ENG-60; D3D12 is the accepted Windows default), 1280×720, greedy meshing.
`gpu_timing_available: true`.

## Full-envelope procedural worldgen + networked graphical capture (ENG-62 / T11a increment 3)

Closes the two oldest open items above: the full `64 x 32 x 64 m` scene, and
graphical capture of the networked run rather than the authoritative sim.

**The scene.** `spall_voxel::fixtures::g1_full_envelope_scene` /
`spall_sim::fixtures::g1_full_envelope_setup` (`Scene::G1FullEnvelope`,
`--scene g1-full-envelope`): real, resident, walkable terrain across the
*entire* `64 x 32 x 64 m` footprint — not just isolated structures in an
otherwise-absent volume (contrast `separated_regions_scene`) — plus a hollow
`4 x 4 x 12 m` tower/bridge spanning brick boundaries, an excavatable ramp
(dirt over stone), and a moving hollow test-volume body.

A first attempt built a real rolling-hill heightmap (a smooth two-axis sine
blend) and hit the actual reason this was open, not the one on record: it
isn't that a dense world is too *expensive* per tick, it's that the terrain
collider's feasibility gate rejects it outright before a single tick runs.
`plan_collider`'s greedy-box decomposition of that heightmap needed 7137 boxes
— over `PRIMITIVE_BUDGET` (4096) — which falls back to the exact native-voxel
collider, whose own feasibility check then rejects the ~6 000 000-cell region
(`ColliderInfeasible::TooLarge`). A **flat plain with one deliberate ramp**
greedy-merges into a handful of large boxes instead (comfortably inside
budget) while still giving a real excavatable slope, not a single bespoke
staircase. Direct brick construction (`Brick::uniform` / `Brick::restored`,
the same trick `giant_collapse_scene`'s block already uses) keeps scene setup
itself cheap regardless: one shared flat-surface brick is built once and
cloned across 62 of the 64 possible-transition bricks, and the other 192
bricks are single uniform inserts.

Measured (this machine, `cargo test -p spall_sim --release --test
g1_full_envelope`): scene build 20.8 ms, `Simulation::new` (collider
construction) 367 ms, mean tick 5.9 µs / worst 177 µs over 200 ticks with the
hollow test-volume body live — three orders of magnitude under the 16.7 ms /
60 Hz budget, so the full 3600-tick / 60 s workload is on the order of tens of
milliseconds of physics time, not "minutes." CPU-side tests (`crates/spall_sim/tests/g1_full_envelope.rs`):
the tower cut detaches the bridge as one body (conservation holds, solid cells
strictly decrease and stay `> 0`); the ramp is ordinary excavatable terrain;
the hollow test-volume body free-falls and settles; two independent runs of
the same script reach the same canonical hash.

**Networked, over real QUIC.** `cargo xtask scenario --name g1-full-envelope`:
a real server + two real `--late-join` clients (the hollow test-volume body is
added to `SimWorld` after construction, bypassing the commit pipeline like
`g4-workload`'s debris, so a live client's fixed-scene baseline would not
match — the same reason `t23-g4-workload.json`'s clients are all `--late-join`).
Client 0 severs the tower (bridge detaches); client 1 digs into the ramp.
Passes clean: both cuts commit, server/both-clients/exact-replay all agree on
one hash.

**Networked graphical capture.** `cargo xtask capture --scene
destruction-networked` (→ `sandbox-capture --scene destruction-networked`)
answers the other open item: it drives the *same* `g1-networked-destruction`
cut script as `--scene destruction` above, but this time against a real
`spall_server::serve` host and **two** real QUIC clients — a plain scripted
"cutter" that performs every cut as a wire `ActionRequest`, and an "observer"
client that never edits, only connects and replicates. `spall_client::net`
gained `ClientNetConfig.on_replica_ready` (a `ReplicaReadyHook`, called once
the observer's baseline is installed) and `ReplicaWorld::now_tick()` (the
newest server tick observed from either a transaction or a motion snapshot,
replica-wide) so a caller can poll the *live, network-replicated* world on its
own schedule instead of driving `spall_sim::Simulation` directly — the capture
loop meshes the observer's `ReplicaWorld` (terrain + every known body at its
latest replicated pose) into the same `spall_render` pipeline `--scene
destruction` uses, at the same five capture ticks. Server, cutter, and observer
run as real Tokio-driven QUIC endpoints over loopback in this one process — the
same pattern `spall_server`'s own `replication_session` / `late_join_session`
integration tests already use, real wire serialization and transport, just not
separate OS processes.

### Measured — this machine, `--scene destruction-networked`

Same adapter/backend/resolution as `--scene destruction`. Three consecutive
runs: `transactions_committed: 10` every time, identical
`final_world_hash` (`d36238c4...`) every time — clean, deterministic
convergence between the observer's replica and the server's authoritative
world (the function itself errors out if they ever disagree). Terrain solid
cells fall 304 → 243, body count and beam-drop progression match `--scene
destruction`'s own numbers tick-for-tick — the same destruction, now proven
through the replication path instead of read directly off the authoritative
sim.

## Scope and remaining gate work

This is CPU-side + networked T11/T11a evidence, not a complete G1 pass. It
does **not** yet cover:

- **The full 60 s / 3600-tick / 10-requests-per-second two-client workload on
  the full-envelope scene**, including the 4 m sphere cut and the 64-brick
  connected-body collapse. The scene now stands up and steps well inside
  budget (above), and the oversized-split replication path those two cuts
  need is available (T17 / ENG-64) — this is now a matter of building the
  sustained request-rate driver and giving the envelope a 64-brick-capable
  structure, not an open feasibility question.
- **Graphical evidence under G2 lighting.** Both `--scene destruction` and
  `--scene destruction-networked` render the destruction path through the T12
  raster pipeline with real GPU pass timings, but debris under colored /
  indirect lighting and the 120+ moving-frame sequence are G2 work (ENG-22).

The commit-latency and admission-accounting **instrumentation** (increment 1)
is in place and asserted; it will measure the full sustained workload once
that driver exists. Graphical capture of both the authoritative sim and the
networked replicated run are wired (`--scene destruction` / `--scene
destruction-networked`).
