## Increment 1 — separated regions, multi-region collapse, late join

Date: 2026-09-10. Branch `feat/eng-30-t23-inc1-separated-regions`.

Adds the bounded-world integrated-acceptance scene and drives the first slice
of the G3 workload — geographically separated players, a multi-region collapse,
and a late join after heavy edits — through the existing multi-process harness.

### Scene: `separated-regions`

`spall_voxel::fixtures::separated_regions_scene` /
`spall_sim::fixtures::separated_regions_setup`, served as
`Scene::SeparatedRegions` (`--scene separated-regions` | `t23-g3` | `g3`).

- One volume **bounded to `256 x 128 x 256 m`** (`32 x 16 x 32` bricks at
  `CellSizeCode::Quarter`) — the G3 operating envelope.
- Two independent collapsible bridge structures: a **west** region at the world
  origin and an **east** region offset by `+72, +0, +72` cells (`+18 m` on `x`
  and `z`). Each is an anchored floor + one slender column + a raised beam the
  column alone holds up. Cutting one region's column detaches only that
  region's beam.
- Only the two regions plus the ground between them are resident, so the
  terrain occupancy grid and every collider rebuild stay CPU-cheap despite the
  large world box.
- Every connecting client gets an authoritative player capsule
  (`Scene::has_players`); `SEPARATED_REGION_SPAWNS` puts **even slots in the
  west region and odd slots in the east region**, so connected players start
  geographically separated. Per-scene spawn tables replace the previous
  unconditional `WALK_ARENA_SPAWNS` (`Scene::player_spawns`).

CPU proof: `cargo test -p spall_sim --test separated_regions` —
`cutting_one_region_leaves_the_other_region_intact` (one column cut detaches
exactly one beam; cutting the other column detaches a second, independent beam;
the two beams' collider regions are one per region; occupied-cell conservation
holds across both cuts) and `both_detached_beams_come_to_rest_on_their_own_floor`
(both freed beams sleep at rest near their floor, neither falls through, the
terrain floors survive).

### Multi-process run: `fixtures/scenarios/t23-g3.json`

`cargo xtask scenario --name t23-g3` launches one `sandbox-server` and four
`sandbox-client` OS processes over real QUIC (optionally behind per-client UDP
loss proxies). Clients 0 and 2 spawn in the west region, client 1 in the east
region. Client 0 severs the west column (~tick 40) and client 1 severs the east
column (~tick 100) — a multi-region collapse detaching one beam per region.
Clients then excavate each region's floor **ends** (outside the beam x-spans, so
each beam keeps a floor to rest on). Client 3 is a `--late-join` replica that
connects after those six edits, pulls a dependency-complete baseline over a
real QUIC bulk transfer, drains the catch-up queue, and lands one cut of its
own.

The harness passes only when: every one of the seven scripted cuts commits; the
server and all four clients agree on the final canonical topology hash; the
committed topology-event stream replayed from the tick-0 baseline
(`sandbox-server --replay`) reproduces that hash; and every detached body is
reported at rest (`require_body_settled`).

late-join client reports a smaller `disp` because it connects after the beams

sensitivity, not a transport defect — the same transfer succeeds every time it
is given until the last scripted edit to finish. A dedicated impaired-late-join
stress with an explicit bounded-failure assertion is still an open item.

## Increment 2 — cold restart and recovery round-trip

Date: 2026-09-10. Same branch.

Adds a `restart_check` flag to the scenario harness and turns it on for
`t23-g3`. After the normal run and the exact-replay check, the harness:

1. stops the run's server (which writes a shutdown checkpoint), then
2. launches a **fresh** `sandbox-server --serve --save` over the same
   `world.db` — a cold recovery from the shutdown checkpoint plus the durable
   journal, with **no client edit replay from world creation** — and requires
   its recovered `final_world_hash` to equal the agreed hash, then
3. connects a fresh `--late-join` client to the restarted server and requires
   it to converge to that same hash: the recovered world serves a correct
   baseline.

All three are gate requirements (`requirements_met` fails otherwise), and the
run's `summary.json` gains `restart_checked`,
`restart_recovered_hash_matches`, `restart_reconnect_hash_matches`, and
`restart_recovered_world_hash`.

#### Measured

| Run | Recovered server | Late-join reconnect | Result |
| --- | --- | --- | --- |
| loopback, no loss | `passed`, 300 ticks, 0 committed, hash `cac2893c…d18e6de` = agreed | `passed`, 0 applied, 288 motion, hash `cac2893c…d18e6de` = agreed | passed |
| main run at `--loss-percent 3` | hash = agreed | hash = agreed | passed |

The recovered server commits nothing (no edits to make) — it only has to come
up and serve one late-join baseline of the post-collapse world. The reconnecting
client applies zero transactions and still converges, because a `--late-join`
replica pulls the full current baseline rather than replaying edits.

`world_hash` is topology (cells + ownership), not float poses, so the recovered
hash is exact across the restart despite physics re-initialisation.

Still open on this row: **traverse away and back** (residency eviction + reload
along a path) before the save — tracked as row 8b below, needs the residency
budget knob from row 7.

## Increment 3 — persistence crash matrix: every boundary + corruption + disk-full

Date: 2026-09-10. Same branch.

Brings `cargo xtask crash-test --suite persistence`
(`spall_server::persist::run_crash_suite`) from 7 scenarios to **12**, so the G3
"crashes at every persistence transaction boundary plus truncated/corrupt data
and disk-full injection" requirement is a single command rather than that
command plus three separate `cargo test` invocations.

The suite's scripted workload is now three committed transactions (sever the
column, then excavate both floor ends) instead of one, so the durable journal
has an interior record for the gap case.

New scenarios:

| Scenario | Injects | Recovery must |
| --- | --- | --- |
| `crash_mid_checkpoint_rows` | `CrashPoint::MidCheckpointRows` | ignore the partial 2nd checkpoint; recover cp0 + full journal |
| `crash_after_checkpoint_commit` | `CrashPoint::AfterCheckpointCommit` (ack lost, data durable) | resume from the **new** checkpoint, not cp0 + replay |
| `journal_crc_corruption_truncates_and_fails_closed` | a CRC-broken journal row (`spall_store::inject::break_journal_crc`) | report corruption, end the durable prefix before it; `RequireClean` fails closed, `AcceptDurablePrefix` resumes from the clean prefix |
| `interior_journal_gap_truncates_and_fails_closed` | a deleted interior journal row (`spall_store::inject::remove_journal_row`) | stop at the record before the gap; same fail-closed / prefix contract |
| `disk_full_on_checkpoint` | `FaultPlan::disk_full` (`SQLITE_FULL` on the checkpoint commit) | no false ack, writer poisoned, fall back to cp0 + full journal |

`spall_store` gains `FaultPlan::disk_full` (a labelled out-of-disk failure at
the commit short-circuit, same shape as `fail_*_commit`) and a `#[doc(hidden)]`
`spall_store::inject` module with `break_journal_crc` / `remove_journal_row`
(direct row mutation on a closed DB — the same technique
`spall_store/tests/durability.rs` already uses). CPU proof for `disk_full`:
`cargo test -p spall_store --test durability disk_full`.

## Increment 4 — impaired late join: bounded explicit failure

Date: 2026-09-10. Same branch.

`docs/validation.md` G3: *"Retry/catch-up stress must terminate with either
successful join or a bounded explicit failure while connected clients
continue."* Increment 1's `t23-g3` already covers the **successful-join** half
(clean and at 3% loss). This increment covers the **bounded-failure** half with
an explicit assertion, and makes a failed late join distinguishable from a hang
or a silent partial state.

- `sandbox-client`: a `--late-join` replica that cannot obtain a baseline now
  writes a structured `{ "result": "join-failed", … }` summary and exits with a
  distinct code (`4`) instead of exiting with no summary. It was already
  *prompt* — `perform_late_join` returns on the first failed transfer, the
  server owns the retry budget — this makes the outcome *legible*.
- `session.rs`: a new `late_join_may_fail` scenario flag. When set, a
  `late_join_clients` replica is accepted if it **either** converged to the
  agreed hash **or** ended in a bounded explicit failure — a `join-failed`
  summary **and** a real process exit (`exit_code.is_some()`; a deadline kill is
  `None` and is rejected as a hang). The live (non-late) clients and the server
  must still agree on one hash and the committed stream must still replay to it.
  `summary.json` gains `impaired_late_join_bounded_failure`.
- `fixtures/scenarios/t23-g3-impaired-join.json`: three live clients run the
  two-region collapse and converge, the run reaches body-settle quiescence, and
  the server shuts down; client 3's `--late-join` connect is delayed to `12 s`,
  well past that shutdown, so its baseline transfer cannot start. Deterministic
  — no reliance on a particular packet-loss draw.

#### Measured

```
sandbox-client: passed  ... hash=c2d5047d…afe7   (x3 live)
sandbox-server: passed ticks=287 clients=3 committed=6 hash=c2d5047d…afe7
sandbox-server: replay passed topology_events=6 hash=c2d5047d…afe7
sandbox-client: transport: timed out after 5s          (client 3, late)
session passed
```

`summary.json`: `result: passed`, `impaired_late_join_bounded_failure: true`,
`all_hashes_match: true`, `requirements_met: true`; the `per_client` row for
client 3 is `result: "join-failed"`, `hash_matches_server: false`, and
`client3.summary.json` carries `"result": "join-failed"`, `"connected": false`,
`"detail": "transport: timed out after 5s"`. Exit code `4`.

`t23-g3` (the successful-join half) still passes unchanged after this change.

## Increment 5 — residency-aware world hash (design)

Date: 2026-09-10. Design only — no code. Superseded by the increment-6
amendment; see `docs/reports/G3-residency-hash.md`.

The blocker: `SimWorld::world_hash()` / `ReplicaWorld::world_hash()` fold
**resident bricks only** and both ends converge by comparing that value, so
evicting a clean terrain brick mid-run breaks convergence, replay, and every
gate assertion. T18 built the whole `ResidencyController` (+ a separate stable
*checkpoint* hash) but deliberately left `serve()` unwired for this reason.

## Increment 6 — logical topology contract + digest foundation (slice A)

Date: 2026-09-10. Same branch. Amends the increment-5 design per
`docs/reviews/2026-09-10-g3-residency-handling.md`, and implements slice A.

The review rejected a reporting-only hash fix: transaction validation (parent
`result_hashes` + the replica's full candidate-volume hash), structural staging
(`ResidencyMode::AllResident`), baselines/repair (`baseline::capture_transfer`,
`brick_repair_patch`), recovery, and `total_solid_cells` all also read
resident-only state. `docs/reports/G3-residency-hash.md` is rewritten as the

digests, each key once, missing ≠ air, modified-air retained), the existing
`canonical_topology_hash` / `spall.topology.v1` records unchanged, the digest
record + lifecycle in `spall_voxel` (a *parallel* record, not an overload of
`GraphBrickMeta`), sim + client adapters producing the same canonical records
without importing the server, the digest lifecycle table, the known-empty rule,
client-scope limits (first server slice keeps client eviction off; no regional
baseline smuggled in), the 6 serve-loop boundaries, the memory/observability
list, and a slice A–E plan with paired-run acceptance.

**Slice A implemented:**

- `spall_voxel::logical` — `BrickDigest { revision, content_hash, solid_cells,
  modified_air }`; `EvictedBricks` with the full lifecycle (`record` /
  `record_from` / `verify_reload` / `clear` / `supersede` / `clear_all`,
  conflict + mismatch rejection); `logical_bricks(volume, evicted)` (resident ∪
  evicted, each key once, canonical `(z,y,x)` order, errors on a

- `spall_sim::canonical_logical_volume_for(volume, evicted, owner)` — the adapter

## Increment 7 — transaction + structural correctness on the logical view (slice B)

Date: 2026-09-10. Same branch.

The commit path (`spall_sim::commit` parent `result_hash`), the replica's
candidate-hash validator (`spall_client::replica`), whole-world conservation
(`SimWorld::total_solid_cells`), and staging (`stage_edit` `pre_solid` /
`post_solid`) all read resident-only state. Slice B makes every one of them use
the **logical** brick set, and makes an edit that needs geometry it cannot see
a hard error rather than a silent corruption.

- `SimWorld` and `ReplicaWorld` carry an optional per-volume `EvictedBricks`
  (empty by default → byte-identical to today; `world_hash` folds
  `canonical_logical_volume_for`). `SimWorld::evict_brick` /
  `clear_evicted_after_reload` implement the evict / reload digest transitions;
  a full baseline clears the namespace on both sides.
- The parent transaction `result_hash` and the replica's per-`result_hash`
  candidate check fold resident ∪ evicted digests, so a server and a replica
  that have **different** bricks evicted still agree and converge.
- Conservation (`total_solid_cells`, staging `pre_solid` + `post_solid`) is over
  the logical solid count — exact no matter where the evicted bricks are.
- `stage_edit` returns `StageError::EvictedGeometryRequired` (snapshot
  untouched) when the edit writes, structurally borders (its touched bricks and
  detached components, grown one brick), or — at commit —
  `CommitError::EvictedGeometryRequired` when the collider rebuild would sample
  an evicted brick. A far, edit-irrelevant eviction is left alone.

#### Measured

`cargo test -p spall_sim --test logical_commit` (4) — evicting an untouched
terrain brick moves neither the parent `result_hash`, `world_hash`, nor
`total_solid_cells`; hash + conservation stable across a non-canonical eviction
order; a cut whose support path runs through an evicted brick is refused with
the snapshot untouched; a cut clear of the evicted brick still stages and
balances its ledger. `cargo test -p spall_client --test logical_residency` (3) —
a replica that has evicted clean bricks still `Published`-validates a
full-server transaction and converges; the server's reported `world_hash` is
unchanged before/after it evicts a clean brick. `cargo fmt --all --check`;
`cargo clippy --workspace --all-targets --all-features -- -D warnings`;
`cargo test --workspace --all-features` — green (the `spall_net` two-process
QUIC test is the known flake; passes on rerun).

Deferred to slice C: dependency-complete reload-and-retry so a far,
edit-irrelevant eviction stops blocking a commit; the `KnownEmpty` membership
rule. Residency stays default-off.

## Increment 8 — backing + capture (slice C)

Date: 2026-09-10. Same branch.

Makes residency **usable**: an edit that needs an evicted brick's cells reloads
it, and the late-join / repair capture paths serve a complete world from an
evicted server.

- `spall_sim::BrickBacking` trait + `MemoryBacking` (durable source of brick
  geometry). `SimWorld::set_backing` + `reload_brick` / `reload_bricks` — load
  from the backing, reinstall, `verify_reload` against the retained digest, drop
  the digest. A `KnownEmpty` result installs an air brick at the retained
  revision (adds no new canonical brick).
- The edit pipeline catches `EvictedGeometryRequired` from **stage and
  commit**, reloads the named bricks, and re-stages the intent next tick. No
  backing, or an `Unavailable` record → a bounded explicit
  `evicted geometry unavailable` rejection with nothing mutated.
- `spall_server::logical_world_baseline` / `logical_capture_transfer` /
  `logical_brick_repair_patch` fill evicted bricks from the backing, so a late
  joiner or a one-brick repair still reaches the exact canonical hash.
  `world_baseline` / `brick_repair_patch` are the `backing = None` cases,
  byte-unchanged when nothing is evicted.

#### Measured

`cargo test -p spall_sim --test logical_reload` (3) — a seam cut whose region
needs an evicted brick reloads it and commits to the same `world_hash` as a
fully resident run; with no backing it is rejected cleanly and the world is
untouched; a wrong backing record is refused by `verify_reload` and keeps the
digest. `cargo test -p spall_server --test logical_baseline` (3) — a late-join
baseline over an evicted server reconstructs the full topology on a fresh
replica (`world_hash` equal); a repair patch covers an evicted brick at the
right revision; `world_baseline` is byte-unchanged with no evictions.
`cargo fmt --all --check`; `cargo clippy --workspace --all-targets
--all-features -- -D warnings`; `cargo test --workspace --all-features` — green.

Deferred to slice D: routing `ResidencyController::enforce_budget` through
`SimWorld::evict_brick`, bridging the durable store to `BrickBacking`, and
checkpoint capture via `ResidencyController::capture_checkpoint` in the serve
loop. Residency stays default-off.

## Increment 9 — default-off serve-loop residency wiring (slice D)

Date: 2026-09-10. Same branch.

Wires the logical-view machinery (slices A–C) into `serve()` behind a
**default-off** knob, so a run can actually evict terrain bricks mid-session and
still converge / replay / restart to the byte-identical hash.

- `ServeConfig.residency: Option<ResidencyLimits>` (`None` → every prior run is
  byte-unchanged). `sandbox-server --residency-budget-bricks N`
  [`--residency-radius-bricks R`]; `session.rs` forwards
  `residency_budget_bricks` / `residency_radius_bricks` from a scenario file.
- `spall_server::residency_pass::ResidencyPass`: owns an `Arc<MemoryBacking>`
  seeded from the terrain and installed on `SimWorld`. Each tick after commits it
  keeps a Chebyshev brick box around every player capsule resident and evicts
  out-of-interest terrain after `EVICT_SETTLE_TICKS` consecutive out-of-interest
  ticks (hysteresis so it does not thrash against the edit pipeline's
  reload-and-retry). `on_commit` refreshes the backing for the bricks an edit
  touched; `reload_all` runs before every periodic **and** the shutdown
  checkpoint so `persist::capture` always snapshots the whole world.
- Late-join baseline and brick-repair capture now call
  `baseline::logical_capture_transfer` / `logical_brick_repair_patch` with the
  pass's backing (`LateJoin.backing`), so a joiner or a repair over an evicted
  server still reconstructs the exact canonical hash.
- `spall_sim::commit`: a collider-rebuild `ExtractError::Unresident` now returns
  **every** evicted brick in the volume (not the single named cell's brick), so
  one reload makes the candidate's whole bounding box resident and the retry
  commits the next tick instead of the residency pass re-evicting an
  already-reloaded brick before the set is whole.
- `ServeSummary` bumped to **version 4**: `residency_evictions_total`,
  `residency_reloads_total`, `resident_terrain_bricks_{min,max,final}`,
  `residency_budget_miss_ticks` (all `0` when residency is off).

#### Measured

`cargo test -p spall_server --test residency_pass` (2): a live `Simulation`
driven twice from the identical edit script — once with `ResidencyPass`, once
without — reaches the **same** `world_hash`, `total_solid_cells`, and
per-transaction `result_hashes` trace, while the pass actually evicts
(`evictions_total > 0`, resident terrain count drops below the start, the
out-of-interest region is evicted when its cut arrives) and the edit pipeline
reloads on demand (`retried > 0`); with no `install` the run is a bit-exact
no-op (`has_backing` / `has_evicted` false).

`cargo xtask scenario --name t23-g3-residency` (`t23-g3` +
`--residency-budget-bricks 6 --residency-radius-bricks 0`):

| --- | --- | ---: | ---: | ---: | ---: | :-: | :-: | --- |
| loopback, no loss | passed | 545 | 7 / 7 | 56 / 7 | 2 / 9 | 7 events → match | recovered + reconnect match | `cac2893cf5e76d866c9c1111b97fe0f822a86e9956f56f3d3ee3a8740d18e6de` |

## Increment 10 — client reload digest lifecycle (slice E1)

Date: 2026-09-10. Same branch.

Slice D leaves the replica fully resident. Before wiring client eviction into
the live session (E2), the replica needs to survive a brick coming *back* —
whether at the same revision (a traversal reload) or a newer one (an
authoritative repair patch that healed a `before` gap) — without ever carrying a
brick that is resident **and** still in its retained-digest set (which
`logical_bricks` rejects, so `world_hash` would panic).

- `spall_voxel::EvictedBricks::drop_resident(volume) -> usize` — drop every
  retained digest whose brick is resident again in `volume`. Idempotent; the
  "Repair / commit" step of the digest lifecycle.
- `spall_client::ReplicaWorld`: `apply_baseline_patch` and the
  transaction-commit path call `drop_resident` for every volume they touch, so a
  repair patch that reloads an evicted brick supersedes its digest atomically.

## Increment 18 — G4 workload: closes the 18/20 transaction-count gap (row 12)

Closes the gap increment 17 left open. **Increment 17's timing hypothesis was
wrong** — instrumented and re-derived with certainty this time, not
speculated.

Diagnosis method: `ActionStatus::Rejected` had no visibility anywhere (server
log or client summary), so the first step was adding it, not guessing further.
`spall_client::net::ClientSummary` gained `action_requests_rejected` /
`action_reject_reasons` (a bounded log of the actual reason strings — the
scripted-action retrier already only resends a `"throttled"` rejection, so
anything else was previously silently lost); `tools/xtask/src/session.rs`
mirrors both into `summary.json`'s `per_client` rows.

First run with that instrumentation showed **all 8 clients** reporting the
same 2 rejection reasons — misleading, and itself a real second bug (see
below), not the cause of the 18/20 gap. A temporary file-backed request/tick
log (since removed) pinned the true cause exactly: the two rejected requests
were request `4` (client 0's tick-500 blast) and client 4's tick-1100 blast —
exactly the two 8-cell-radius "blast" cuts, nothing else, ever.

**Root cause:** `t23-g4-workload.json`'s two blast cuts (`cell: [20, 1, 1]`
and `[92, 1, 73]`, `radius: 8`) request a sphere whose centre sits only 1 cell
above the world's `y = 0` (and, for the west blast, `z = 0`) floor. An
8-cell-radius sphere centred there extends to cell `-7`, landing in brick
`y = -1` (`z = -1` for the west blast) — outside the declared volume bounds,
rejected by `spall_sim::stage::StageError::OutOfBounds`. This server runs with
`ServeConfig::dev_unvalidated_actions` (`dev_intent_from_request` trusts
`claimed_brush` verbatim — no server-side raycast or reach check, unlike the
production `resolve_intent` path), so the rejection is 100% deterministic on
every run, independent of tick order, network timing, or which client sends
it. Fixed by moving both blast centres to `y = 12` (and the west blast's `z`
to `12`) — comfortably inside bounds (sphere floor at cell `4`) while staying
within the populated region.

**Second, independent bug found and fixed along the way** (this is what made
the first diagnostic run's data misleading): `spall_server::serve`'s
tick-report loop `broadcast()`s every `ActionStatus` (`action_statuses(&report)`
— commits *and* rejections) to **every connected client**, not just the
session that staged the request. `ActionStatus` carries no owner, so every
non-owning client's `ActionStatus::Rejected` reads as if it were its own — the
retrier only acts on a `"throttled"` reason so this was previously harmless in
effect, but corrupts exactly the kind of per-client diagnostic this increment
added. Fixed: a new `submitted_by: HashMap<RequestId, SessionId>` records who
staged each request; the tick-report loop now `send_to`s the resolved status
to only that session (falling back to the old broadcast only if the map has
no entry, which should not happen).

Verified: `cargo xtask scenario --name t23-g4-workload --timeout-ms 240000`
now reports `session passed`, `20`/`20` transactions committed,
`requirements_met: true`, `all_hashes_match: true`, `actions_rejected: 0`,
every client's `action_requests_rejected: 0`. Exact replay (20 events) and
cold restart (recovered + reconnect) both matched. Full checks rerun: `cargo
fmt --all --check`, `cargo clippy --workspace --all-targets --all-features --
-D warnings`, `cargo test --workspace --all-features` — all green, no
regressions.

Row 12 is now **fully passing** on the standard harness for this proof-run
scope; rows 13–14 (the sustained 2-minute/30-minute measured soak and

## Increment 20 — row 15 root-caused, row 16 fixed, row 10 follow-up: server half proven, a genuine client/protocol gap found (not fixed)

Three independent investigations, landed together. None of the three needed
new gate infrastructure beyond what increments 17–19 already added; all three
work purely by exercising already-shipped mechanisms harder.

### Row 15 — root-caused to `rapier3d`, mitigation confirmed, regression pinned

PR #99 reported "a freshly-spawned player near `x = 0` on a bounded volume
doesn't respond to horizontal input for hundreds of ticks" and suspected
"broad-phase/query-pipeline warm-up". Reproduced directly at the
`spall_physics` level (no `spall_sim`/`spall_voxel` pipeline involved) and
systematically ruled out every plausible cause:
- **Not warm-up**: extra `world.step()`s before the character exists make no
  difference (contra the original speculation).
- **Not representation-specific**: `Representation::NativeVoxels` reproduces
  it identically to `MergedCuboids` — `spall_physics::merge::greedy_boxes`
  is not the cause.
- **Not "one combined collider"**: still reproduces with the floor and the
  elevated structure as two separate physics bodies.
- **Position/geometry-dependent, not simply "near x=0"**: a floor plus a
  narrow *column* alone does not reproduce it; a floor plus the wide, thin
  *beam* alone does, at its original position — move that beam much higher
  or much further away (spawn unchanged) and it stops reproducing. The exact
  trigger inside `rapier3d::control::KinematicCharacterController::move_shape`
  was not isolated further; this is a genuine upstream defect, not something
  in this codebase.
- The shipped mitigation (`SEPARATED_REGION_FAR_SPAWNS`'s `x = 7 m` slot-0
  spawn) is empirically confirmed: `x >= ~6.5 m` does not reproduce it on
  this exact scene.

`crates/spall_physics/src/character.rs` gained a permanent, `#[ignore]`d
regression test pinning the *current broken* behaviour
(`row15_elevated_beam_near_origin_freezes_horizontal_movement`) — if a
`rapier3d` upgrade ever fixes this, the test starts failing when run with
`--ignored`, which is the signal to remove the `#[ignore]` and reconsider the
spawn-distance mitigation.

**New, separate discovery while isolating row 15** (not row 15 itself, not
fixed here): `crates/spall_sim/tests/separated_regions.rs` gained
`plain_scene_spawn_falls_through_the_floor_instead_of_walking_it`, pinning
that a scripted walk from `x = 7` on the *plain* `separated_regions_setup`
scene (not the full-envelope one) falls straight through the floor
(`grounded` stays `false`, `y` falls unbounded) instead of walking it. Does
not reproduce on `separated_regions_full_envelope_setup` at the same `x` —
the two scenes' terrain differs only in their east-region offset and the
resulting `terrain_collider_region` union-box shape, so the divergence is
somewhere in occupancy extraction for that wider/shorter box specifically.
Never previously exercised: no prior scenario scripted movement on
`separated_regions_setup` (only stationary spawns, or the unrelated
`walk_arena` scene via `t23-g3-traversal`).

### Row 16 — fixed: `distance_travelled_m` now reads authoritative, not predicted

Root cause matched the reported symptom exactly once traced through
`spall_client::predict`: `PlayerMovementSummary::distance_travelled_m` was
computed from `self.predicted`, but the mover only advances prediction while
`ClientPhysics::covers` holds (increment 16) — a residency reload round trip
legitimately *holds* (does not advance) predicted for a while, the same
mechanism the adjacent `at_rest` check in `spall_client::net` already
accounts for by reading `authoritative()` instead. If a run's final summary
happened to be captured while predicted was held but authoritative had
already progressed further, the reported distance under-reported a run that
converged correctly everywhere else — exactly "the predictor's own
bookkeeping was the casualty, not the simulation" from PR #99's report.
Fixed: `summary()` now computes `distance_travelled_m` from
`self.authoritative`, which "keeps updating from every snapshot regardless"
(same reasoning as the existing `at_rest` check) and never has this gap.
`max_distance_from_start_m` (a running max, used for out-and-back proofs)
was already immune to this — it never regresses — so it is unchanged.

**New, separate discovery while verifying the fix** (not row 16 itself, not
fixed here): four runs of `t23-g3-full-envelope` (2 failed, 2 passed) showed
the fix working correctly where it applied — `distance_travelled_m` was
sane in every run — but one failure was a *different* gate,
`held_button_release_ok: false`, with the player's final
predicted/authoritative position around `y = -80 m` (fallen through the
world after the scripted traversal, off the far edge of the causeway). This
is the T19 "a lost button-up cannot leave it walking forever" acceptance
bullet, not row 16's predictor-staleness mechanism — a client that does not
release its held movement input at the end of a scripted leg can walk off
the far edge into the void. Not diagnosed further or fixed here.

### Row 10 follow-up — the server-side retry/catch-up-exhaustion mechanism is proven; a real client/protocol gap was found alongside it, not fixed

`t23-g3-impaired-join.json` already proves row 10's "bounded explicit
failure" half for a late joiner that never gets a baseline at all (connect
delayed past server shutdown). The open half was "retry/catch-up exhaustion
while connected clients stay active" — nobody had built a scenario that
actually drives a joining client's catch-up queue past `catch_up_cap`
repeatedly while other clients keep committing. Built one
(`fixtures/scenarios/t23-g3-retry-exhaustion.json`) and its supporting
harness wiring:
- `tools/xtask/src/session.rs` gained a `retry_exhaustion` scenario field
  (mirroring `join_budget`'s existing "shape only the named client" proxy
  pattern) that also passes `--catch-up-cap` / `--max-join-retries` through
  to `sandbox-server` (both CLI flags already existed on `ServeConfig`; the
  scenario harness had never wired either).
- The fixture: clients 0–2 commit 24 tightly-spaced cuts (client 3 owns none
  of them) while client 3 late-joins immediately behind a shaped proxy with
  `catch_up_cap: 1`.

**Calibration finding**: the shaped proxy governs the *entire* connection,
not just the bulk baseline transfer, so bandwidth/loss low enough to
guarantee queue overflow (initially tried: 128–1000 B/s) also blows the
unrelated 5 s QUIC handshake timeout before the client ever reaches
`Phase::Joining` at all (`late_join_retries` stayed `0` — it never even
registered as joining). Needed a much higher bandwidth (50,000 B/s, proven
to let the handshake complete) and a very tight, front-loaded edit cadence
(24 commits starting at tick 10, 8 ticks apart) instead, so multiple commits
land inside every catch-up window regardless of transfer speed.

**Verified working as designed**: `server.summary.json` shows
`late_join_retries: 2`, `late_joins_failed: 1` — `LateJoin::fan_out_transaction`'s
existing recapture-on-overflow path fires repeatedly and correctly gives up
once `max_join_retries` is exceeded, exactly as increment 11's original
design intended. This is real, previously-unexercised proof that the
**server-side** half of "retry/catch-up stress must terminate with... a
bounded explicit failure" (`docs/validation.md`) works.

**Genuine gap found, not fixed**: the run still reports `session FAILED` —
not because the server behaved wrongly, but because the *disconnected
client* does not turn a mid-catch-up `Outbound::Shutdown` into the bounded
`"join-failed"` exit `late_join_may_fail` expects. Two compounding causes,
both in shared code far outside this scenario's scope to patch safely here:
1. `Outbound::Shutdown`'s `Bye` reason is the literal string `"server
   complete"` whether the run ended normally *or* a client's retries were
   exhausted (`crates/spall_server/src/serve.rs`) — indistinguishable at the
   source.
2. Even if the reason were distinct, nothing could currently read it:
   `spall_net::conn`'s control-stream reader discards a received `Bye`'s
   reason unconditionally (`NetMessage::Bye { .. } => return Ok(None)`) —
   there is no wire-level signal a client could act on today.
3. Separately, `spall_client::net`'s late-join `progressed` check
   (`config.late_join && baseline_bricks > 0`) is satisfied by the *first*
   baseline the client ever installed, before any catch-up drama — so a
   client dropped mid-exhaustion still reports `result: "passed"` with a
   stale, non-converged hash instead of failing explicitly. A silently wrong
   "passed" is a worse outcome than the hang this row exists to bound.

This needs a deliberate wire-protocol change (a distinguishable Shutdown
reason, actually surfaced past the transport layer) plus a client-side fix,
not a rushed patch alongside a test-authoring pass — filed as open, same
treatment as rows 15/16 above. The fixture is committed as an accurate,
reproducible demonstration of both the working server mechanism and the gap
— **a passing run of it should not be expected**, and one should not be read
as proof retry/catch-up exhaustion is fully handled. Read
`server.summary.json`'s `late_join_retries` / `late_joins_failed` (non-zero)
as the proof the server half already is.

Evidence: `cargo fmt --all --check`; `cargo clippy --workspace --all-targets
--all-features -- -D warnings`; `cargo test --workspace --all-features` (all
green, 73 test binaries, no regressions); `cargo test -p spall_physics --lib
row15 -- --ignored` (fails, confirming the defect is still present); `cargo
test -p spall_sim --test separated_regions
plain_scene_spawn_falls_through_the_floor_instead_of_walking_it` (passes,
confirming that finding); `cargo xtask scenario --name t23-g3-retry-exhaustion
--timeout-ms 60000` (fails as described above — server counters prove the
mechanism, client result does not yet reflect it).

Rows 15 and 16 are now **documented / fixed** to the extent described above;
row 10 remains **open** — the server-side half is now proven, the
client/protocol half is a newly-scoped, real gap.
